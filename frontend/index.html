Defects found and fixed

  • Critical
    Patients could see other patients' reports when they signed up with the same name or email. Fix: bookings are linked to the account, not matched by name/email.
  • High
    Any logged-in user could open any booking (phone, address) by changing the ID in the URL. Fix: only the patient, the booking's centre or an admin can open it.
  • High
    Report PDFs were reachable by public URL without logging in. Fix: permission-checked downloads; uploads must be real PDFs.
  • High
    Centre status changes were saved only in the browser. Fix: status is stored in the database.
  • Medium
    Booking API had CSRF protection disabled and no server-side validation. Fix: CSRF re-enabled; invalid dates, fields, tests and centres rejected.
  • Medium
    “Book Now” while logged out led to a 404 instead of the login page. Fix: LOGIN_URL set; users return to the page they wanted.
  • Low
    The “Today” filter showed yesterday's bookings before 6 AM. Fix: Bangladesh local time instead of UTC.
  • Low
    Mobile menu never opened; dead links; unverifiable homepage claims. Fix: menu toggle added, links checked, only true numbers shown.

3 of the 8 are security issues (data exposure and access control). Each fix is guarded by regression tests.

Automation & what I learned

71 tests using Django's test framework in accounts/tests.py (30) and bookings/tests.py (41). They cover login, roles, booking validation, CSRF, report permissions and the regressions above.

A passing test isn't always a good test. My first test for the “Book Now → 404” bug only checked that the redirect contained /login/, and the broken URL /accounts/login/ contains that too. I rewrote the assertions to check the exact URL and that the page loads, then confirmed the new tests fail without the fix (6 failures) and pass with it.

Case study 02

UI & API automation — Playwright and Postman/Newman

Automation assignment from my SQA course (Ostad): end-to-end UI tests against the SauceDemo practice store and API tests against the reqres.in practice API.

  • Playwright (JavaScript)
  • Postman
  • Newman
  • Allure
  • Repository (opens in a new tab) ↗
  • Page Object Model version (opens in a new tab) ↗

Testing scope

UI — SauceDemo (3 end-to-end tests)
  • Locked-out user sees the correct error message
  • Standard user buys 3 items: cart badge, item names, subtotal, tax and total
  • Performance-glitch user sorts Z→A, buys the first item; total computed from the live price
API — reqres.in (9 requests, 19 assertions)
  • Register and log in; user ID and token saved as variables
  • GET, PUT and PATCH a user; fields and updatedAt checked
  • Negative cases: missing password (400), wrong email (4xx), unknown user (404)

Defects: none logged. SauceDemo and reqres.in are public practice targets, so this project is about automation design and assertions, not finding product bugs.

Automation setup

  • Playwright Test with headless Chromium, run sequentially (1 worker), screenshots on failure
  • List, HTML and Allure reporters
  • Postman collection with chained environment variables, run from the CLI by Newman with an HTML (htmlextra) report

Run it yourself

npm install
npx playwright install chromium
npm test            # 3 Playwright UI tests
export REQRES_API_KEY=<your key>
npx newman run postman/reqres-collection.json \
  -e postman/reqres-environment.json \
  --env-var "apiKey=$REQRES_API_KEY"

  • Allure: 3 test cases, 100% passed
